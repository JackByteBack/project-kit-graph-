A

Workflow

Every session runs in one named mode. README is written last so the index always matches the files.

  1. Mode: Inspect

    Inspect

    Read the repo, manifests, configs, tests, and existing docs. No writes.

  2. Mode: Select

    Select

    Apply triggers. Classify each candidate Required, Recommended, Optional, or Not needed.

  3. Mode: Document

    Create

    Core set first, then conditional docs. Unknowns stay Open; ideas stay Proposed.

  4. Mode: Review

    Validate

    Headers, links, index coverage, secret patterns. Then check facts and diagrams by hand.

  5. Mode: Document

    Report

    List what was created, decided, and still open. State which checks actually ran.

Implement A separate gate. Code changes happen only when the task says so, inside the authorization tiers below, followed by tests, doc updates, and a current-state entry.

D

Knowledge status

Every document carries one header status. Individual statements carry their own label, plus the kind of evidence behind them.

Confirmed

Verified by the owner or by authoritative project evidence.

Set by Claude, citing the source

Proposed

A recommendation that nobody has approved yet.

Set by Claude

Open

Missing, uncertain, or waiting on a decision.

Set by Claude

Accepted

A proposal the owner explicitly approved.

Owner only

Rejected

Considered and declined, with the reason on record.

Owner, with reason
E

Ten rules

These apply to every project, every session.

  1. R1One subject per file. One home per fact; link instead of copying.
  2. R2Explicit status. Label what is Confirmed, Proposed, or Open.
  3. R3Never invent facts. No made-up schemas, endpoints, approvals, or test results.
  4. R4Protect secrets. Names and policies only, never values.
  5. R5Keep decision history. Supersede an entry; never overwrite it.
  6. R6Update current-state.md at the end of every substantive session.
  7. R7Approve dependencies and data flows before adding them.
  8. R8Stay maintainable. About 4 KB is a prompt to review, not a limit.
  9. R9No empty docs. Say what is unknown and what would settle it.
  10. R10Preserve the project. Don't restructure code to fit the docs.

Start a project

Copy the kit into a new folder, then generate only the documents the project needs.

Scaffold
python scaffold.py init --name "My App" \
  --preset web-app --out ../my-app
Custom triggers
python scaffold.py init --name "My App" \
  --triggers ui,db,auth,sensitive --also setup
Check
python scaffold.py validate
Refresh index
python scaffold.py readme
Document graph
python scaffold.py graph

G

Name only to site

Give the kit a project name and an agent with web search. Three fresh sessions take it from a name to a reviewed build, and every handoff is a file.

Create the project folder
python scaffold.py new "My Project"
Only the prompt, to attach anywhere
python scaffold.py prompt "My Project" \
  --details "audience, goals, links" \
  --out my-project-prompt.md
  1. Session 1 · Research

    Generate

    Give the agent PROMPT-GENERATOR.md. It researches the name, logs every source, and writes research/ and BUILD-PROMPT.md.

  2. Session 2 · Build

    Build

    Fresh context, give it BUILD-PROMPT.md. It works in verified loops and reads and writes memory/.

  3. Session 3 · Review

    Review

    Fresh context again, with the adversarial review prompt. It reports findings and fixes nothing.

NeedsSession 1 needs web search and file write. Without web access the agent says so and stops at an Open-item skeleton rather than guessing.
